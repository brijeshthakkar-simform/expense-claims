# SQL proof report: data integrity on a real PostgreSQL

> Written 2026-10-13 during planning, before any app code exists. It proves that the integrity SQL in [03 §16](../../design/03-data-model-and-integrity.md#16-verified-sql-migration-by-migration) works on a real PostgreSQL. Re-verified independently from this folder: **127/127**, no processes left behind.
> Inputs: [00-decisions-and-contracts.md](../../design/00-decisions-and-contracts.md) (authoritative), the data design, and the DB rows of the red-team review.
> Outputs: [`verified.sql`](verified.sql) (the SQL that passed, laid out by migration) and [`schema.prisma`](schema.prisma) (Prisma 7.10, validated).
> Harness: [`harness/`](./harness/) (see §7). No Docker needed: it downloads real PostgreSQL binaries via `embedded-postgres`.
>
> ```bash
> cd docs/reference/sql-proof/harness && npm ci && node build.mjs && node run.mjs all
> ```
>
> It takes about 90 s, prints `127/127 passed` and leaves no processes running. `harness/out/migrations-full/` holds the five assembled `migration.sql` files (Prisma DDL + hand SQL); in P0 the real migrations are regenerated by `prisma migrate dev --create-only` and the hand SQL is pasted from [03 §16](../../design/03-data-model-and-integrity.md#16-verified-sql-migration-by-migration). Migration 3 in 03 has two extra lines added after the proof; P0 confirms them.

## 0. Verdict

**127/127 tests passed** on PostgreSQL 18.4. The attacks ran as the least-privilege role `expense_app`, using up to 12 concurrent connections.

- **The stored, trigger-maintained total (D-12) is proven. The D-13 Plan B gate is not needed.** Canonical's five P0 spike tests (a)–(e) pass on the P0 migration subset alone (0001–0003). Every desync path we attacked was refused or self-healed:
  - API-shaped writes, Prisma model operations, raw SQL, a CTE, a GUC, upsert, MERGE and COPY;
  - overflow;
  - four concurrent interleavings plus a 300-transaction storm;
  - owner sabotage, caught at COMMIT.
- **The approved lock, the state machine, the chain-shape rules, the audit-completeness rules and the privilege model behave as canonical says**, with three SQL defects fixed (§4). Each defect is reproduced on a throw-away database by reverting just that piece (tests BUG-1, BUG-2), or was caught by a failing test (P0-f).
- **The Prisma side is consistent.** All three checks agree that the migrations, the live database and `schema.prisma` match, with no drift:
  - `prisma migrate deploy` (as `expense_owner`) applies all 5 migrations;
  - `migrate diff` from the live DB to `schema.prisma` is empty, and so is `migrate diff` from the migrations (replayed in a shadow DB) to `schema.prisma`;
  - `migrate dev --create-only` generates an empty migration, twice.
- **The Prisma 7.10 error shapes are now facts, not guesses** (§5). `readSqlState()` as written in §5 maps all 11 probed cases correctly, including the error thrown at COMMIT.

## 2. What was assembled (and where it deviates from canonical)

Five migrations, in canonical C-23 order. Each `migration.sql` is the Prisma-generated DDL plus hand SQL. The Prisma DDL was produced by `prisma migrate diff` between staged schemas: P0 tables, then plus workflow, then plus receipts.

| Migration | Contents |
|---|---|
| `0001_init` (P0) | hand-**prepended** `claim_number_seq` + `next_claim_number()`; then Prisma creates departments, users, sessions, categories, claims, line_items and their indexes. `claims.current_submission_id` exists here with its UNIQUE index but **without an FK**, because `claim_submissions` does not exist yet. |
| `0002_integrity_core` (P0) | CHECKs; #1 `assert_claim_editable` v1, #2 `line_items_before_write`, #3 `line_items_recompute_claim_totals`, #4 `claims_guard` v1, #5 `assert_claim_total_consistent`; view `v_claim_total_drift` |
| `0003_privileges` (P0) | explicit grants for the P0 tables, the view and the sequence |
| `0004_workflow` (P3) | Prisma creates 4 enums, tiers, submissions, steps, events, the `current_submission_id` FK and the partial indexes. Then hand SQL: CHECKs, **#1 v2**, #6 `claim_submissions_verify` v1, #7 `approval_steps_guard`, #8 `forbid_mutation`, #9 `assert_transition_audited`, **#4 v2**, the triggers and the grants. |
| `0005_receipts` (P6) | Prisma creates `receipts`. Then hand SQL: CHECKs, #10 `receipts_before_write`, **#6 v2**, grants. |

There are 11 functions (10 PL/pgSQL plus `next_claim_number()`, which matches canonical's budget) and 14 triggers. The trigger names are exactly canonical C-04's, and the J10 test asserts them.

**Deviations the design docs must carry.** Each one is either a fix or a decision canonical left open:

1. **`0004` also replaces `assert_claim_editable` (v2, snapshot freeze).** A claim is not editable while a submission exists with `revision > current_revision`, which raises UC002. This closes BUG-2 (§4).
2. **`0005` also replaces `claim_submissions_verify` (v2).** It checks that the snapshot's receipts exactly match the live receipts. Canonical C-23 lists only #10 for 0005.
3. **Snapshot verification is stricter than D-18's four fields.** The line multiset is compared on `lineItemId, expenseDate, categoryId, categoryCode, categoryName, glCode, amountMinor, description, merchant`. The header is compared on `v = 1, title, currency, totalMinor`. The `claimant` block must exactly equal `{id, employeeCode, name, email, departmentCode}`, and receipts are compared too (v2). All mismatches raise UC016.
   - Why: the export and the dispute view read the snapshot's GL code, names and storage keys, so those must be unforgeable too.
   - What is not checked: extra keys inside line objects, and line order. The service must copy the live values verbatim (no re-trimming).
4. **`claims_guard` → SUBMITTED** checks two more things:
   - The submission's `total_minor`, `line_item_count` and snapshot title still match the claim (UC016).
   - Each step's `tier_code` and `applies_above_minor` equal the *k*-th applicable active tier (UC012), as well as the count and level checks canonical already requires.
5. **The claim-number rule** (fix for BUG-1). For `expense_app`, the trigger keeps the number only when it equals the one the column DEFAULT just drew in this session (`currval`). Otherwise it draws a fresh number. A supplied number is never kept.
6. **`claims_guard` v1 (P0) allows only DRAFT→SUBMITTED and SUBMITTED→DRAFT.** Approvals arrive with 0004. A P0 "submit" is `UPDATE claims SET status='SUBMITTED', current_revision=1, current_submission_id=uuidv7()`; the FK does not exist until 0004. This is enough for spike (b).
7. **Error precedence** (fix for BUG-3). An illegal transition always reports UC005, checked before the UC010 rule for DB-owned fields. The step guard likewise reports UC005 for an illegal step transition before UC010.
8. **DB-owned timestamps**:
   - `created_at` is stamped by the DB for `expense_app` on `claims`, `claim_submissions` and `approval_steps`, as well as on the D-23 list.
   - For the owner, a timestamp supplied at a transition is kept (the seed's `SeedClock`); if none is supplied, `now()` is used.
   - Changing `submitted_at`, `approved_at`, `rejected_at`, `activated_at`, `decided_at` or `cancelled_at` outside its own transition raises UC010 for **every** role.
9. **Roles and hygiene**:
   - `01-roles.sh` uses `REVOKE ALL ON DATABASE … FROM PUBLIC`, a superset of `REVOKE TEMPORARY`, and `REVOKE ALL ON SCHEMA public FROM PUBLIC`, then grants USAGE to the app.
   - The view is `WITH (security_invoker = true)`.
   - Two CHECKs were added: `claim_events_payload_object` and `claim_events_rejection_reason`.
10. **Prisma emits `ON UPDATE CASCADE` on every FK by default.** This is harmless: every referenced id is immutable (UC010) or not writable by the app. It is left as generated so there is no schema noise.

**Other findings the plan should carry.** These are not SQL defects.

- **`prisma migrate diff --from-migrations` needs an existing shadow database.** Without one it fails with `P1003`. CI must either create it (`CREATE DATABASE … OWNER expense_owner`) and pass `SHADOW_DATABASE_URL`, or rely on `migrate dev`, which creates its own shadow DB because the owner has CREATEDB.
- **The claim-first lock is not optional.** Raw multi-row line writes that skip `lockOwnedClaim` deadlock routinely (D8b), because the BEFORE ROW trigger locks the line row and then the claim. Integrity holds, but availability suffers. Services must lock the claim first and retry `40P01`.
- **`SET CONSTRAINTS ALL IMMEDIATE` before a line write breaks the write** with a spurious UC009. Immediate row-level constraint triggers fire before the AFTER STATEMENT recompute. It fails closed, but app code must never use it (J13).
- **TC-I20's name "approve racing recall: exactly one wins" is only true for the final approval** (D11-final). For an intermediate level both succeed, in order (D11-approve). The test catalogue should say so.
- **Prisma nested create returns the DB-derived total** (4200 in the probe) because Prisma re-reads after nested writes. Services should still re-read the DTO, as C-25 already says.

## 5. Prisma 7.10 + `@prisma/adapter-pg` error shapes (recorded, all asserted)

| Path | Error | Where the SQLSTATE lives |
|---|---|---|
| Model op (`update`, `updateMany`, `create`, `createMany`, `deleteMany`), including inside `$transaction(async tx => …)` | `PrismaClientKnownRequestError`, `code = 'P2039'`, `meta.modelName` | `meta.driverAdapterError.cause.originalCode` (also `.code`), `kind: 'postgres'`, `originalMessage = '<API_CODE>: …'` |
| `$executeRaw` / `$queryRaw` | `PrismaClientKnownRequestError`, `code = 'P2010'` | same `meta.driverAdapterError.cause` |
| Unique violation (23505) | `PrismaClientKnownRequestError`, `code = 'P2002'` | `meta.driverAdapterError.cause = { kind: 'UniqueConstraintViolation', originalCode: '23505', constraint: { index } }`. **There is no `.code` here**, so read `originalCode` first. |
| **Deferred trigger at COMMIT** of an interactive transaction (UC015, UC009) | a raw **`DriverAdapterError`** (not a Prisma known error) | `err.cause.originalCode` (also `err.cause.code`) |
| node-postgres (`pg`) in tests and scripts | `DatabaseError` | `err.code` |

The verified implementation for `src/server/db/pg-error.ts` maps all 11 probed cases correctly:

```ts
export function readSqlState(err: unknown): string | undefined {
  const e = err as any;
  return (
    e?.meta?.driverAdapterError?.cause?.originalCode ??   // P2039 / P2010 / P2002
    e?.meta?.driverAdapterError?.cause?.code ??
    e?.cause?.originalCode ??                             // DriverAdapterError thrown at COMMIT
    e?.cause?.code ??
    (typeof e?.code === 'string' && /^[0-9A-Z]{5}$/.test(e.code) ? e.code : undefined) // pg DatabaseError
  );
}
```

The HINT (`RECALL_TO_EDIT`) is not exposed on the Prisma error. The service sets `details.hint` itself, which C-06 already does.

## 6. Caveats, limits and accepted residuals

- **Version and runtime.** The proof ran on PG **18.4**, not the 18.6 image, on bare-metal embedded Postgres rather than Docker or Testcontainers. Nothing used is new in 18.5 or 18.6 (`uuidv7()`, `MAINTAIN` and transition tables are all present in 18.4). Re-run the converted suite on `postgres:18.6-trixie` in P0.
- **No application code was exercised.** The "service layer" is a SQL fixture (`lib/fixtures.mjs`) that follows C-25 write orders exactly; the routes, `defineRoute` and Zod are not exercised. HTTP codes in this report are canonical's mappings, not observed responses.
- **Not enforced by the DB, by design.** These need their own app-level tests:
  - `claims.claimant_id = actor` and "the event's actor is the authenticated user". There are no GUCs (R-04); the scoped query proves identity.
  - The approver is the *right* manager (D-21 deferred). The DB checks the chain shape, tier copies and eligibility, not the reporting line; TC-I16 compares against `buildChain()`.
  - The 50-lines limit, 5 receipts per line, and the reject-reason and comment *presence* rules. The reason's length *is* a CHECK.
  - Stand-alone events (G11).
- **Owner and superuser can still disable triggers.** The readiness probe (J9) and `v_claim_total_drift` detect it. The UC009 deferred check catches total sabotage even then, unless the deferred trigger is disabled as well. Owner credentials stay out of the app (D-34).
- **Snapshot verification blind spots.** Extra keys inside line objects and line order are not verified.
- **Costs.**
  - The commit-time total check runs one indexed SUM per changed line.
  - The claim-number rule opens a plpgsql sub-transaction (`EXCEPTION` block) per app claim insert. Both are negligible at POC scale.
  - The perf seed must **commit in batches**, because deferred-trigger events queue in memory until COMMIT.
- **Partial indexes depend on Prisma's `partialIndexes` preview.** It works in 7.10 with the `where: raw("(status = 'PENDING'::approval_step_status)")` spelling, which matches what Postgres stores, so there is no drift.

## 7. Harness approach: turning it into Vitest integration tests

**Pipeline** (`run.mjs`):

1. Start the cluster.
2. Run the superuser SQL from `01-roles.sh` (`sql/00_roles.sql`, per database).
3. Run `prisma migrate deploy` with `MIGRATE_DATABASE_URL` set to the owner (`prisma.config.ts` reads `PRISMA_MIGRATIONS` / `PRISMA_SCHEMA`).
4. Seed the reference data and the C-15 cast **as the owner**.
5. Run the suites over three kinds of `pg` connections: `expense_app` (attacks and services), `expense_owner` (sabotage and fixtures) and `postgres` (monitor only).
6. Run the drift checks and the Prisma client probe.
7. Stop the cluster.

In Vitest, `tests/helpers/global-setup.ts` does steps 1–4 with Testcontainers (`01-roles.sh` mounted, as D-42 says) and exposes `appSql`, `ownerSql` and `monitorSql`.

**Recipes that made it work.** Put these in `tests/helpers/db.ts`.

- **`rejects(code, fn)`** asserts the exact SQLSTATE. Deferred errors only appear at COMMIT, so wrap the whole transaction:

  ```ts
  await rejects('UC015', () => tx(app, async () => { /* ... */ }))
  ```

- **Proving a block, not a sleep.** Read `pg_backend_pid()` *before* starting the blocking statement, because a pg `Client` queues later queries behind a blocked one. Start the statement and attach `p.catch(() => {})` so a later rejection isn't unhandled. Then poll from a **superuser or `pg_monitor`** connection until `pg_stat_activity.wait_event_type = 'Lock'` (a non-superuser can't see other roles' wait events). Then COMMIT the holder and `await p`.

  ```ts
  const pid2 = await pidOf(app2); await app.query('BEGIN'); await insertLine(app, c, 100);
  await app2.query('BEGIN'); const p = insertLine(app2, c, 200); p.catch(() => {});
  ```

- **Gates for deterministic races.** A third connection holds `SELECT … FOR NO KEY UPDATE` on the claim until a promise resolves. The contenders queue in a known order, and releasing the gate lets them run (D7, D11).
- **Short timeouts in tests.** `SET lock_timeout = '300ms'` on one connection exercises 55P03 without waiting 5 s.
- **Reset.** Owner `TRUNCATE claims, line_items, receipts, claim_submissions, approval_steps, claim_events, sessions` works despite the circular FK and fires no row triggers (J14). Keep `afterEach(assertTotalsInSync)` = `SELECT * FROM v_claim_total_drift` must be empty.
- **Gotchas.**
  - pg returns `name[]` as a string; cast with `::text[]`.
  - pg parses `int8` (`tx_id`) to `BigInt` if you register the parser.
  - Return `timestamptz` as text when comparing instants exactly.
- **Fixtures and attacks.** Build fixtures through C-25-shaped helpers and attack them with hooks: `submit(c, id, actor, { snapshot, chain, event, beforeClaimUpdate, beforeCommit })`. Every forgery test is then one line.
